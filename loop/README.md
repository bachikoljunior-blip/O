# loop/ — 周回のあいだ、覚えていられないことを置く場所

このゲームは、区切りのない改善ループで作られています。ループを回すセッションは
永遠には続きません。文脈が伸びれば要約されて薄れますし、落ちることもあります。
そのとき失われるのは、コードではなく**判断の理由**です。何を目指していたのか、
何を試して駄目だったのか、次に何をするつもりだったのか。

ここにある2つのファイルが、それを持ちます。

| ファイル | 何が書いてあるか | いつ変わるか |
|---|---|---|
| [`RUBRIC.md`](RUBRIC.md) | 何を目指しているか。追う軸と、追わない軸 | ほとんど変わらない |
| [`state.json`](state.json) | いまどこまで来ているか。次に何をするか | 毎周 |

## 1周のやりかた

1. **`RUBRIC.md` と `state.json` を読む。** 特に `tried` を読む。同じ壁に二度ぶつからない
2. `lock` を見る。`startedAt` が45分以内なら、別のセッションが作業中。**何もせず終わる**
3. `lock` を自分のもので上書きして push
4. `backlog` の先頭を1つ取って、やる
5. **実際に動かして確かめる。** 通ったら `rubric` の該当項目を `pass` にし、`evidence` に
   どう確かめたかを書く。確かめていないなら `unknown` のまま
6. commit / push
7. `state.json` を更新する — `backlog` から消す、`tried` に足す、`handoff` に次の人への
   申し送りを書く、`lock` を外す
8. 時間があれば 4 に戻る

## backlog に何を入れるか

**`rubric` の `unknown` か `fail` を1つ減らす手**を入れてください。それ以外の思いつきは、
入れる前に「どの項目が動くのか」を書けるか確かめてください。書けないなら、たぶん要りません。

止まる条件はありません。ただし**やることが尽きたと感じたら**、それは backlog が
空なのではなく、`rubric` の `unknown` を確かめていないだけです。まずそちらをやってください。

## tried に何を入れるか

**試して駄目だったこと**です。うまくいったことは commit を見れば分かるので書かなくて
構いません。ここに書く価値があるのは、次のセッションが同じ判断をして同じ時間を
溶かすのを防げることだけです。「なぜ駄目だったか」まで書いてください。

## lock について

45分で失効します。1周が15〜25分なので、その2倍弱です。落ちたセッションのロックが
残り続けると、ループが二度と動かなくなります。

作業が45分を超えそうなら、途中でも `lock.startedAt` を打ち直してください。
